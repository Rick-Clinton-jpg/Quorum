# Review Board — Adversarial Test Report

**Skill under test:** `~/.claude/skills/review-board/SKILL.md` (personal skill, confirmed saved and discoverable via the skill listing)
**Method:** Six independent, cold-context subagent runs, one per round, each acting as both "user" and "skill" and then self-critiquing against a stated adversarial goal. Depth was answered "full review" every round (never "quick pass"). Artifact was answered "no" for rounds 1–5 and "yes" only for round 6. Each round ran stages cumulatively (1 through the target stage) and was manually stopped immediately after the target stage's output, even where the skill might naturally have continued.

## Description-triggering accuracy across the six domains

Assessing whether the skill's `description` field would plausibly cause it to auto-trigger if each round's request had been typed cold, without explicitly invoking review-board:

- **Round 1 (ambiguous one-liner, "build me a dashboard"):** Strong match — squarely "build... something non-trivial" with ambiguity the description calls out explicitly.
- **Round 2 (coding, "add caching to a slow endpoint"):** **Weak/ambiguous match.** This is exactly the kind of request where review-board adds real value (multiple viable engineering approaches, Round 2 proved that), but the description's own exclusion — "skip for simple one-step requests... or trivial fixes" — could plausibly cause a model to classify "add caching" as a small, well-scoped technical task and skip the skill entirely, never reaching the point where its value showed up in this test.
- **Round 3 (writing/content, Docker guide):** **Weak match.** The description's trigger verbs ("build, implement, create, or design") and framing ("mistakes would be costly to redo") read as software/engineering-centric. A pure writing/content request doesn't obviously read as "non-trivial" or "costly to redo" even though Stage 3's prior-art step turned out to be genuinely valuable for it.
- **Round 4 (business/strategy decision):** Strong match — the description explicitly says "before starting any significant build, implementation, **or decision**," which covers this case well.
- **Round 5 (coding/security decision, build-vs-buy auth):** Strong match — "especially when multiple approaches are plausible, mistakes would be costly to redo" fits this scenario almost exactly.
- **Round 6 (coding/business hybrid, browser extension):** Strong match — clear build/implement request.

**Summary:** Triggering accuracy is strong for anything phrased as a "build/implement" request or an explicit "decision," but has two real blind spots: (1) small-sounding engineering tasks that actually hide multiple approaches, where the "skip trivial fixes" exclusion can misfire, and (2) non-software writing/content deliverables, which aren't well-represented in the description's example verbs despite the skill working fine on them once invoked.

## Prioritized fixes before release

**High priority**
1. **Stage 3 lacks an enforced independence/impact check.** Add a concrete self-check to the Stage 3 instructions (e.g., "before finishing, name what changed in Stage 2 as a result of the second pass — if nothing changed, say so and justify why the two queries were still independent"). Currently both "meaningfully reworded" and "folds into Stage 2" are aspirational language with no verification step, so a lower-effort or adversarial run could satisfy the letter of the rule with a synonym-swapped query and a cosmetic footnote.
2. **Stage 6's approval bar is underspecified.** Add explicit examples of what does and doesn't count (this test's three probes — vague affirmation, topic change, silence — are good canonical examples to bake into the skill text itself rather than leaving them to be reinvented each run). Also add guidance for partial/conditional post-Stage-6 approval, which the current "Notes" section doesn't cover (it only addresses pre-Stage-6 interruptions).
3. **Description under-triggers for two real domains.** Tighten the description to (a) explicitly note that a request's apparent small size doesn't exempt it if multiple genuinely different approaches exist (the "add caching" case), and (b) explicitly include written/content deliverables and non-engineering decisions alongside "build, implement, create, or design," so the skill doesn't read as software-only.

**Medium priority**
4. **Stage 4 doesn't require weighting rationale to be disclosed.** Round 4's run volunteered a clear, well-justified weighting scheme, but nothing in the skill mandates disclosing *why* criteria are weighted as they are — make that explicit so scoring stays legible by default, not by good faith.
5. **No cross-check between Stage 4 scores and Stage 5 findings.** Round 5 surfaced a real (if minor) inconsistency — a high Stage 4 score on a criterion ("control") that Stage 5 then argues doesn't actually hold up. A light instruction to reconcile the two stages would catch this class of internal contradiction.

**Low priority**
6. **Stage 2's "cosmetic vs. genuine" distinctness rule has no worked example**, leaving borderline calls (Round 2's app-tier vs. edge-tier caching) to interpretation. One clarifying example in the skill text would reduce variance across runs.
7. **Stage 1 has no instruction to prioritize among multiple open questions** when several surface at once — a UX nicety, not a correctness issue.

None of these are release-blocking in the sense of causing an outright failure — all six adversarial rounds passed on their core behavioral goal. The common thread is that several of the skill's most important safeguards (search independence, Stage 2 impact, scoring rationale, approval clarity) are currently *instructions* rather than *enforced checks*, which worked in every run tested here but leaves headroom for a lower-effort or adversarial execution of the same skill to technically comply while cutting the corner the instruction was meant to prevent.
